# Agent 对话语义展示设计

日期：2026-08-10

## 目标

对话面板只展示两类自然语言内容：模型真实生成的公开执行说明，以及任务全部成功后的真实最终回答。宿主预设的开场、编排和完成文案不得作为 Assistant 内容进入实时流、持久化快照或历史重放。

连续操作按照用户可见的自然语言边界分组，不按照 Run、Unit、阶段或进度事件等内部边界拆分。

## 非目标

- 不把完整剧本文档正文放进最终对话消息。
- 不隐藏模型真实生成的公开执行说明。
- 不删除工具名称、阶段名称等操作记录自身的标签。
- 不改变思考内容的开启、关闭和权限配置。
- 不用前端字符串黑名单掩盖后端已经持久化的固定文案。

## 当前问题

当前链路存在三个互相关联的问题：

1. Planner、任务投影和终态处理会生成“请求理解”“剧本创作任务”等宿主固定文案。
2. 子 Run 的模型最终内容被正确隔离后，任务终态又使用“剧本任务已完成，候选稿已生成……”替代，导致真实最终回答消失。
3. 前端按照 Run、Unit 或工具批次创建操作区域，连续操作即使没有自然语言隔断，也会形成多个并列的收起区域。

这不是单纯的 CSS 问题。内容来源、终态生成和时间线分组需要使用同一套语义边界。

## 采用方案

采用“后端明确内容语义，前端按语义确定性分组”。

后端负责保证流中不存在宿主伪造的 Assistant 文案，并提供一次真实最终回答。前端负责把规范化事件投影为文本和操作组，不使用具体模型、工具或业务阶段名称判断分组。

不采用以下方案：

- 仅前端过滤固定字符串：无法修复持久化数据和历史重放，也会遗漏新增文案。
- 后端预先生成 UI 操作组：会把展示结构固化进业务协议，降低复用性。

## 后端内容契约

### 公开执行说明

只有模型实际生成并被标记为公开说明的内容才能投影为 `commentaryDelta`。它可以来自模型普通公开文本，也可以来自协议中明确由模型拥有的 `executionSummary` 等公开摘要字段。宿主只能做必要的空白规范化和敏感内容裁剪，不能改写、补充固定前后缀，或把结构化状态拼接成 Assistant 自然语言。

需要移除的来源包括但不限于：

- Planner 的“请求理解：”前缀；
- 任务开始时的“剧本创作任务”等固定对话文案；
- 宿主为模型公开摘要添加的固定前后缀，以及根据状态凭空拼接的 commentary；
- “结构化剧本任务已完成”“剧本任务已完成，候选稿已生成”等固定终态文案。

工具名称、Unit 名称和阶段名称仍可作为结构化操作记录的标签，但不能成为对话文本。

### 真实最终回答

剧本正式任务增加 `compose_final_response` Unit：

```text
collect_evidence
  -> generate_candidate
  -> validate_candidate
  -> compose_final_response
  -> publish_candidate
```

多目标任务中，`compose_final_response` 依赖所有 `validate_candidate` Unit；`publish_candidate` 依赖 `compose_final_response` 和全部校验结果。

`compose_final_response` 是无工具、有限输出的模型调用，只接收：

- 用户原始请求；
- 实际完成的交付物类型和范围；
- 已校验候选稿的标题；
- 可公开的执行摘要；
- 保留项和约束的完成情况。

它不能接收完整正文、结构化 JSON 或内部 Trace，也不能生成或猜测 Revision URL。输出是一段面向用户的自然语言结论。

该输出作为 Unit checkpoint 持久化，但在 `publish_candidate` 成功前不得进入对话。发布成功后，服务把这段真实结论写入 Turn 的 `assistant_content`，前端根据真实 Revision 引用附加候选稿入口。

最终回答不使用固定文案兜底。若模型最终回答 Unit 失败，任务进入可恢复暂停；若发布失败，已完成的最终回答 checkpoint 被保留，恢复时只重试发布。

### 单次发布约束

任务只有在以下条件同时满足时才能发出正式回答：

- 所有业务 Unit 完成；
- Revision 已成功发布；
- `compose_final_response` 有已持久化的非空模型输出；
- Turn 尚未发布过正式回答。

实时和重放都从同一持久化事实生成结果，禁止 child Run 的结束文本直接终结父任务。

## 前端时间线分组

前端先把事件归一为三种可见项：

- `Narrative`：模型真实生成的公开执行说明；
- `Operation`：工具调用、工具结果和可展示的阶段操作；
- `FinalAnswer`：任务终态的真实回答和交付物入口。

归并规则：

1. 收到 `Operation` 时，如果最后一个可见项是操作组，则追加到该组；否则创建一个操作组。
2. 收到非空 `Narrative` 时，结束当前操作组并插入文本。
3. 收到 `FinalAnswer` 时，结束当前操作组，并把最终回答作为独立 Assistant 内容展示。
4. Run、Unit、阶段、进度刷新、reasoning 事件和 SSE 批次变化都不是分组边界。
5. 空文本、固定状态文本和不可见内部事件既不创建可见项，也不拆分操作组。

因此，以下事件：

```text
Operation A
Run changed
Unit changed
Operation B
Progress refresh
Operation C
```

形成一个收起区域；而：

```text
Operation A
Narrative: 正在核对人物连续性
Operation B
```

形成“操作组、真实说明、操作组”。

该归并器必须同时用于实时流和历史重放，避免刷新页面后分组改变。

## 暂停、恢复和错误

- `paused` 不生成最终回答，也不生成固定解释文案。
- 恢复不会重复展示已持久化的公开说明、操作或最终回答。
- 可恢复失败保留已经完成的操作组、最终回答 checkpoint 和候选稿 Artifact。
- 永久失败只显示真实错误状态；不得用成功型固定文案填补空内容。
- 用户取消时保留已显示的真实说明和操作记录，不伪造总结。

## 测试要求

### 后端

- 固定开场、Planner 前缀和固定完成文案不会进入 chunk、Turn 或重放数据。
- `compose_final_response` 只能看到受控的公开完成事实。
- 最终回答 Unit 完成但发布失败时，不输出正式回答；恢复发布后复用 checkpoint。
- 暂停和子 Run 完成不能产生父任务最终回答。
- 成功任务只持久化和投影一次真实最终回答。

### 前端

- 跨 Run、Unit 和阶段的连续操作归并为一个操作组。
- 真实 `commentaryDelta` 是唯一的公开文本分组边界。
- reasoning、进度和空事件不会拆组。
- 实时处理和重放生成完全相同的时间线。
- 暂停、恢复和刷新不会重复操作组或最终回答。

### 架构门禁

- 禁止已删除的固定文案重新出现在生产对话投影代码中。
- 禁止使用文案字符串、模型名称或工具名称决定操作分组。
- 禁止 child Run 的 `finalResponse` 直接写入剧本父 Turn。

## 验收标准

完成一次包含多个连续工具调用的剧本任务后，用户应看到：

1. 没有固定开场编排文字；
2. 没有真实说明隔断的连续操作只有一个收起区域；
3. 模型真实说明保留，并自然分隔操作组；
4. 没有固定完成文案；
5. Revision 成功发布后出现一次真实自然语言结论和候选稿入口；
6. 刷新页面后内容、顺序和分组保持不变。
