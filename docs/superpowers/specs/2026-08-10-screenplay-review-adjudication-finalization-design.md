# 剧本审阅裁决与人工定稿设计

日期：2026-08-10

## 目标

将剧本项目的“审阅修订”从由 Agent 结论控制的强门禁，改造成由确定性校验、Agent 审阅建议和用户最终裁决共同组成的“审阅与定稿”阶段。

Agent 可以发现问题、提出修订建议并给出是否适合定稿的建议，但不能自行把项目标记为完成。项目只有在当前剧本通过确定性校验、当前审阅意见全部得到明确处理，并且用户主动点击“确认定稿”后，才进入 `completed`。

## 当前问题

当前项目状态由审阅 Revision 的结构化 `verdict` 直接决定：`ready` 进入 `completed`，`revise` 或 `major_rework` 继续要求生成修订稿。这个设计存在三个问题：

1. Agent 对节奏、人物动机、对白和风格的判断具有主观性，却被当成不可推翻的项目事实。
2. 用户无法把误报标记为“不成立”，也无法明确表示“知道风险但决定保留”。
3. “审阅任务已经完成”和“整个项目已经定稿”被混成同一个状态。

现有 Markdown 编辑只改变审阅文档的可读文本，不应通过修改 Agent 原始报告来伪造新的结构化结论。用户裁决必须作为独立业务记录保存。

## 采用的方案

采用“确定性硬校验 + Agent 软审阅 + 用户显式定稿”的混合模式。

- 硬校验由系统执行，只覆盖可以客观证明的问题。
- Agent 审阅报告是不可变的建议和证据来源，`verdict` 只表示 Agent 的推荐。
- 每条审阅意见都有独立、可审计的用户处理状态。
- 所有意见都明确处理后，“确认定稿”才可用。
- 无论 Agent 是否给出 `ready`，最终完成都必须由用户点击产生。

不采用以下方案：

- 继续由 Agent `verdict` 自动完成项目：无法处理误报，也剥夺用户的最终创作决定权。
- 允许用户在未阅读或未处理意见时直接定稿：虽然灵活，但容易把遗漏操作误认为明确取舍。

## 概念与状态

### 审阅任务完成

Agent 成功生成一份针对当前剧本 Revision 的审阅报告，即表示本次审阅任务完成。报告可以包含任意数量的意见，也可以建议 `ready`、`revise` 或 `major_rework`。

审阅任务完成不等于项目完成。

### 审阅意见状态

每条意见初始为 `pending`，用户可以将其处理为：

| 状态 | 用户含义 | 是否允许计入定稿条件 |
| --- | --- | --- |
| `pending` | 尚未作出判断 | 否 |
| `planned` | 接受意见，准备修订 | 否 |
| `resolved` | 已完成修订或用户确认问题已经解决 | 是 |
| `dismissed` | 用户判断该意见不成立 | 是 |
| `riskAccepted` | 用户认可问题存在，但决定保留 | 是 |

“接受意见”和“接受风险”必须分开。接受意见只表示进入待修订状态，不能提前满足定稿条件；接受风险表示用户已经作出保留现状的最终决定。

### 项目完成

审阅意见处理分成两个门禁：

1. 只要存在 `pending`，用户就不能离开意见处理阶段。全部意见作出选择后，如果存在 `planned`，下一步是“开始修订”。
2. 只有不存在 `pending` 和 `planned`，并满足其余定稿条件时，才能启用“确认定稿”。

项目满足以下全部条件时，才能启用“确认定稿”：

1. 当前剧本 Revision 标记为完整。
2. 当前审阅报告确实审阅当前剧本 Revision，不能使用过期报告。
3. 所有确定性硬校验通过。
4. 当前审阅报告中的全部意见都处于 `resolved`、`dismissed` 或 `riskAccepted`。
5. 不存在 `pending` 或 `planned` 意见。

满足条件后项目仍保持“等待用户定稿”，直到用户点击“确认定稿”。点击成功后写入人工定稿事件，项目才进入 `completed`。

可以表达为：

```text
canFinalize =
  currentDraft.isComplete
  && currentReview.reviewedDraftId == currentDraft.id
  && deterministicChecksPassed
  && unresolvedFindingCount == 0

projectCompleted = canFinalize && userFinalizationEventExists
```

## 硬校验与软审阅的边界

硬校验只能包含确定性规则，例如：

- 正文为空或缺少要求的集数。
- 正文引用了不存在的场景或分集。
- 当前审阅报告绑定的不是当前剧本 Revision。
- 文档结构损坏，无法读取或导出。
- 项目所要求的上游正式文档缺失。

硬校验失败不能通过“不成立”或“接受风险”绕过，必须修复对应数据。

以下内容属于 Agent 软审阅：

- 人物动机是否充分。
- 节奏是否拖沓。
- 对白是否自然。
- 情节是否足够有张力。
- 某个伏笔、主题或人物弧光是否表达充分。

即使 Agent 将软审阅意见标记为 `critical`，它仍然是编辑严重程度，而不是系统硬校验。用户可以将其标记为“不成立”或“接受风险”。

## 用户交互

### 审阅意见列表

“审阅与定稿”页面显示：

- 当前审阅针对的剧本版本。
- Agent 的整体建议，但不使用“系统判定通过”一类文案。
- 待处理、待修订、已解决、不成立和接受风险的数量。
- 每条意见的严重程度、描述、涉及场景和当前处理状态。

单条意见支持以下操作：

- 接受并准备修订。
- 标记为已解决。
- 标记为不成立。
- 标记为接受风险。
- 修改之前的处理结果。

“不成立”和“接受风险”允许填写说明但不强制，系统始终记录操作人和时间。

### 批量处理

用户可以勾选部分意见，也可以选择全部待处理意见，然后执行：

- 批量接受并准备修订。
- 批量标记为已解决。
- 批量标记为不成立。
- 批量标记为接受风险。

批量操作必须使用完整含义，不能只显示含混的“接受”或“拒绝”。提交前显示影响数量，例如“将 6 条意见标记为接受风险？”。操作完成后仍允许逐条修改。

`planned` 不提供“一键视为完成”的别名。批量“接受并准备修订”可以把所选意见加入修订范围，但这些意见仍会阻止定稿，直到后续被标记为已解决、不成立或接受风险。

批量操作解决的是逐条点击成本，不降低状态门禁：仍有 `pending` 时不能进入修订或定稿；全部意见完成选择后，有 `planned` 就进入修订，没有 `planned` 才进入等待用户定稿。

### 确认定稿

“确认定稿”始终在审阅阶段可见：

- 有未处理或待修订意见时禁用，并显示“还有 N 条意见待处理”。
- 硬校验失败时禁用，并显示必须修复的客观错误。
- 条件满足时启用，点击后再次展示当前剧本版本、审阅版本和各类裁决数量。
- 用户确认后才提交定稿命令。

当审阅报告没有任何意见时，也必须由用户点击“确认定稿”，不能自动完成。

## 数据所有权

Agent 审阅 Revision 保持不可变，继续保存原始 `verdict`、`issues` 和 `reviewedDraftId`。用户裁决不回写或改写 Agent 报告。

新增独立的审阅裁决记录，逻辑标识至少包含：

```text
projectId
reviewRevisionId
draftRevisionId
issueId
status
note
actor
decidedAt
```

同一 `reviewRevisionId + issueId` 只有一个当前裁决状态，状态修改保留审计事件。批量处理在一个事务中更新所选意见，使用命令 ID 保证重放幂等，并校验项目 Revision，防止旧页面覆盖新审阅结果。

人工定稿使用独立事件保存：

```text
projectId
draftRevisionId
reviewRevisionId
decisionSnapshotHash
actor
finalizedAt
commandId
```

项目的 `completed` 状态从与当前 Head 匹配的定稿事件派生，不再从 Agent `verdict=ready` 派生。

## 版本失效与历史

- 接受新的剧本正文 Revision 后，旧审阅报告、旧裁决和旧定稿事件保留在历史中，但不能继续满足当前版本的定稿条件。
- 新正文必须重新生成或明确取得一份绑定它的审阅报告。
- 复审可以引用上一轮意见及其裁决结果，但必须生成新的审阅 Revision 和新的裁决集合。
- 重新应用上游结构、场景表或正文版本时，现有定稿状态自动失效，项目回到相应创作或审阅阶段。
- 已定稿项目仍可查看当时的审阅报告、每条用户裁决和定稿确认记录。

## 工作流状态

对外仍可保持现有大阶段，避免增加过多导航层级：

```text
draft
  -> review / 等待审阅
  -> review / 等待处理意见
  -> review / 等待修订
  -> review / 等待用户定稿
  -> completed
```

这些是 `review` 阶段的派生子状态，不需要把每一个都升级成项目顶层阶段。主按钮根据子状态显示“开始审阅”“继续处理”“开始修订”或“确认定稿”。

## 错误处理

- 裁决请求引用的意见不属于当前审阅 Revision 时拒绝请求，不静默写入旧报告。
- 批量请求中任一意见无效时整批回滚，避免只处理一部分。
- 定稿命令在服务端重新计算全部条件，不能只相信前端按钮状态。
- 重复提交同一命令返回第一次的定稿结果，不创建重复事件。
- 定稿前项目被其他页面更新时返回版本冲突，前端刷新后重新展示最新状态。
- Agent 报告出现 `ready` 但仍含有意见时，以意见列表为准，所有意见仍需处理。

## 兼容迁移

已有项目不能因为历史 `verdict=ready` 自动生成一条伪造的用户确认记录。

- 已经处于 `completed` 的历史项目保持已完成状态，并标记为旧流程完成，避免破坏已有用户结果。
- 尚未完成的项目进入新流程；已有审阅意见初始化为 `pending`。
- 旧报告无意见时进入“等待用户定稿”，不自动完成。
- 新流程产生的项目完成状态必须有真实的人工定稿事件。

旧流程完成标记必须明确为兼容状态，例如 `completionSource=legacyAgentVerdict`，不能伪装为用户定稿事件。任何在迁移后重新应用正文或上游版本的旧项目都退出兼容完成状态，并按新流程重新审阅和人工定稿。

## 测试要求

### 领域与后端

- Agent `verdict=ready` 但没有人工定稿事件时，项目不能进入 `completed`。
- `revise` 或 `major_rework` 的全部意见被标记为不成立或接受风险后，可以进入等待用户定稿。
- 任一意见为 `pending` 或 `planned` 时，服务端拒绝定稿。
- 所有意见为完成态且硬校验通过时，人工定稿命令成功。
- 硬校验失败不能通过批量裁决绕过。
- 批量裁决原子、幂等，并拒绝过期的审阅 Revision。
- 接受新正文 Revision 后，旧裁决和旧定稿事件不再满足当前状态。
- 已有 `completed` 项目迁移后保持完成，但不会伪造新流程事件。

### 前端

- 正确显示每种意见状态及数量。
- 支持单条、选中项和全部待处理项的批量接受并准备修订、已解决、不成立和接受风险操作。
- 批量操作显示准确的数量和完整动作名称。
- 存在 `pending`、`planned` 或硬校验失败时，“确认定稿”不可用且原因明确。
- 所有意见处理完成后按钮启用，但项目不会自动完成。
- 用户确认成功后才显示“创作已完成”。
- 刷新页面和切换历史对话后，裁决状态保持一致。

## 验收标准

1. 一份包含 6 条意见的审阅报告中，5 条标记为接受风险、1 条标记为不成立后，可以点击“确认定稿”。
2. 同一报告仍有 1 条待处理时，不能定稿，并明确提示剩余数量。
3. 用户可以选择全部待处理意见，一次批量接受并准备修订，或标记为已解决、不成立、接受风险。
4. 批量接受并准备修订不会把意见错误地视为已处理完成。
5. Agent 建议 `ready` 且没有意见时，项目仍等待用户点击确认。
6. Agent 建议 `major_rework` 时，用户仍可对软审阅意见作出不成立或接受风险的裁决。
7. 任何确定性硬校验错误都不能通过用户裁决跳过。
8. 用户确认定稿后可追溯当时的剧本版本、审阅版本和全部裁决记录。
