# 剧本审阅输入、正文对照与原位编辑设计

日期：2026-08-11

## 目标

这次改造同时解决三个彼此关联的问题：

1. 审阅 Agent 必须实际拿到被审阅版本的剧本正文，不能把内部读取失败写成剧情缺陷。
2. 用户在“项目文档 → 剧本正文”中可以并排查看正文与对应审阅。
3. “基于此版本编辑”不再打开第二层弹窗，而是在当前项目文档工作区内原位进入编辑状态。

项目文档中的剧本正文目前已经可以正常读取。本设计不重做正文存储或基础阅读能力；它修复的是审阅子任务的输入协议，并重新组织项目文档的阅读与编辑交互。

## 已确认的当前问题

### 审阅输入协议矛盾

当前增量审阅流程在宿主侧调用 `episode_context` 取得指定剧本版本的分集上下文，但提交给模型的审阅载荷只包含分集编号、剧本版本 ID、约束和场景 ID，没有包含本集正文。

与此同时，审阅提示词要求模型“按需调用工具读取正文”，而 `candidate_write` 阶段按既有权限边界只开放候选稿写入与检查工具，不开放 `getScreenplayEpisodeContext` 等读取工具。因此正文在项目版本库中存在且可读，但审阅子任务无法访问它。

模型生成的“当前环境没有正文读取工具”属于系统执行失败，不是剧本内容问题，不能进入 `issues`，也不能让用户通过“不成立”或“接受风险”来处理。

### 阅读与编辑重复嵌套

当前 `RevisionLibraryModal` 是一个“目录 + 内容”的项目文档阅读器；点击“基于此版本编辑”后又打开一个具有相同“目录 + 内容”结构的第二层弹窗。第二层弹窗增加了操作步骤，也让阅读状态、编辑状态和关闭行为形成两套重复实现。

### 正文与审阅缺少版本化对照

剧本正文和审阅修订分别作为两个文档角色展示。用户查看审阅问题时不能同时看到对应正文，查看正文时也不能确认当前意见究竟审阅的是哪个正文版本。

## 方案比较

### 方案一：宿主绑定审阅材料 + 单一文档工作区（采用）

宿主在每集审阅开始前构造并校验完整的审阅输入包；项目文档弹窗内部用明确的 `view` / `edit` 状态切换阅读器和编辑器。剧本正文角色提供正文与审阅的并排对照。

优点是审阅依据确定、工具权限边界不混用、界面只有一个工作区，最容易验证和维护。

### 方案二：模型先读取、再切换到候选写入阶段

每集先启动 `evidence_read` 工具循环收集正文，再启动 `candidate_write` 循环生成审阅。它保留按需读取能力，但增加一轮模型调用、阶段交接和中间证据持久化，失败面更大。

### 方案三：同一阶段同时开放读取与候选写入工具

实现改动最少，但会破坏“正式候选写入阶段不混用读取工具”的权限和测试边界，模型也可能在材料不完整时提前写入结果，不采用。

编辑界面也评估过右侧抽屉和保留二级弹窗。抽屉会挤压正文与审阅的对照空间，二级弹窗继续保留重复路径，因此都不采用。

## 审阅执行设计

### 宿主绑定的分集输入

每个分集审阅子任务启动前，由剧本领域应用层从指定 Revision 构造 `ReviewEpisodeInput`。至少包含：

```text
projectId
draftRevisionId
episodeNumber
sceneIds
draftContentText
scenePlan
requiredContext
contentDigest
inputContractVersion
```

- `draftContentText` 必须来自 `draftRevisionId` 指向的不可变 Revision，不能读取当前 Head 后假设它与目标版本相同。
- `scenePlan` 和 `sceneIds` 必须属于同一集，并与正文能够互相校验。
- `requiredContext` 只包含完成当前集审阅所需的创作简报、连续性摘要或相邻集边界，不把完整项目资料重复塞入每个子任务。
- `contentDigest` 由宿主基于正文和必要场景计划生成，用于证明报告实际绑定的输入。
- 输入包只作为运行材料和来源凭据，不在候选 `payload` 与 `contentText` 中重复存储正文。

输入包校验通过后，正文随审阅请求直接提供给模型。提示词改为“宿主已经提供本集正文和场景计划，只能依据这些材料审阅”，不再要求模型调用一个当前阶段不可用的读取工具。

审阅候选写入仍保持 `candidate_write` 权限，只允许 `writeScreenplayCandidatePart` 和 `inspectScreenplayCandidate`。通用 Agent Core 不理解剧本业务；输入构造、校验和审阅结果语义全部保留在剧本领域边界内。

### 分集结果状态

每集审阅结果必须是以下两类之一：

```text
completed
failed
```

`completed` 表示模型收到了经过宿主校验的正文，并产生了合法的 `verdict` 和 `issues`。它记录 `reviewedDraftId`、`episodeNumber`、`contentDigest` 和输入协议版本。

`failed` 是宿主拥有的执行状态，包含稳定错误代码、简短用户说明、是否可重试和关联 Run。模型不能通过候选数据把某集声明为 `failed`。失败状态不能包含 `issues`，原始异常与模型过程文本只保留在运行诊断中。

单集在既有重试策略耗尽后失败时，其他集继续审阅；主动取消和不可恢复的项目级错误仍终止整个任务。

### 聚合报告

审阅 Revision 的结构化内容升级为可表达完整与部分失败的协议，至少包含：

```text
reviewedDraftId
reviewedEpisodes
completedEpisodes
failedEpisodes
issues
verdict
inputContractVersion
```

- `issues` 只聚合 `completed` 分集的内容问题。
- `failedEpisodes` 单独保存失败集及宿主错误信息。
- 存在失败集时，整体报告可以发布用于查看已完成的结果，但不能满足定稿条件。
- 全部集失败时仍保留可诊断的失败记录，任务终态和界面文案必须明确为审阅失败，不能显示“审阅已完成”。
- 支持只重试失败集；重试前必须确认当前剧本仍是同一 Revision。全部失败集成功后生成新的完整审阅 Revision，不原地修改不可变报告。

### 定稿门禁和历史兼容

`derive_review_state` 增加确定性硬校验：

- 当前审阅是否绑定当前剧本 Revision。
- 是否存在 `failedEpisodes`。
- 已完成分集是否具有宿主验证的输入协议版本与内容摘要。

审阅失败不是用户裁决项。用户可以继续处理其他有效意见，但失败集重试成功前不能确认定稿，主操作应指向“重新审阅失败集”。

新报告使用新的输入协议版本。旧流程生成且缺少可验证输入凭据的未完成报告保留在历史中，但不能作为新流程的有效定稿依据；需要基于真实正文重新审阅。已经按旧流程完成的历史项目继续遵循既有 `legacyAgentVerdict` 兼容规则，不伪造新的用户定稿事件。

## 项目文档工作区设计

### 单一弹窗、两种模式

项目文档只保留最外层 `PurrModal`。内部工作区拥有显式模式：

```text
view
edit-clean
edit-dirty
saving
publishing
```

点击“基于此版本编辑”时：

1. 刷新项目状态并确认目标 Revision 仍存在。
2. 恢复同一基础版本的 Working Copy，或从目标 Revision 创建新的 Working Copy。
3. 当前内容区域原位切换为编辑器，不打开第二个 `PurrModal`。

如果已经存在基于其他 Revision 的未发布 Working Copy，继续使用现有“替换未发布编辑内容”确认，不能静默覆盖。

### 工具栏与保存语义

阅读状态显示“基于此版本编辑”和适用的“应用此版本”。进入编辑状态后，操作改为：

- `保存草稿`：更新 Working Copy，不生成项目 Revision，不退出编辑。
- `发布候选版本`：先保存 Working Copy，再生成不可变候选 Revision；成功后退出编辑并选中新版本。
- `退出编辑`：回到同一版本的阅读状态；已保存的 Working Copy 继续保留，方便下次恢复。

保存或发布过程中禁用会改变文档、版本或模式的操作。保存失败时保留本地编辑内容并停留在编辑状态。

### 未保存修改保护

本地编辑值与最后一次成功保存的 Working Copy 内容不一致时，状态为 `edit-dirty`。

以下操作必须经过统一导航保护：

- 切换文档类型。
- 切换版本。
- 退出编辑。
- 关闭项目文档弹窗。

确认框提供：

1. `保存并继续`：保存成功后执行原操作；保存失败则留在当前页面。
2. `放弃未保存修改`：恢复到最后一次成功保存的 Working Copy，再执行原操作；不删除已经保存的 Working Copy。
3. `留在此处`：取消导航。

在同一 Working Copy 内切换分集不触发确认。各分集的本地修改保留在当前编辑状态，用户可以连续修改多集后统一保存。

## 正文与审阅对照设计

### 剧本正文角色

选择“剧本正文”时保留左侧分集目录，右侧内容区域按桌面宽度分为：

- 正文约 62%。
- 对应审阅约 38%。

阅读状态下左栏渲染正文 Markdown；编辑状态下左栏原位切换为 `KnowledgeMarkdownEditor`。右栏始终只读，并明确显示审阅版本及“基于 vN 的审阅”。

两个内容栏拥有固定栏头和独立滚动区域，项目文档弹窗外壳不滚动。窄屏下不强行维持过窄分栏，改为“正文 / 审阅”标签切换。

### 精确版本与分集匹配

审阅只在以下条件同时满足时展示：

```text
review.reviewedDraftId == selectedDraftRevision.id
reviewEpisode.episodeNumber == selectedDraftEpisode.episodeNumber
```

存在多份匹配报告时默认展示最新发布的匹配 Revision，并在栏头显示版本。旧报告仍可通过“审阅修订”文档角色查看，不在对照栏增加第二套完整版本管理器。

选择“文档概览”时，左栏显示剧本概览，右栏显示整份审阅摘要。发布新的正文候选版本后，如果还没有对应审阅，右栏进入明确的未审阅状态，不沿用旧版本意见。

右栏需要区分四种状态：

- `已完成，有意见`：显示当前集问题列表和修改方向。
- `已完成，无意见`：显示“本集未发现需要处理的问题”。
- `审阅失败`：显示失败集状态、简短原因和重新审阅入口，不渲染为问题卡片。
- `尚无对应审阅`：说明当前正文版本还没有匹配报告。

对照栏只承担阅读。`planned`、`resolved`、`dismissed`、`riskAccepted` 等用户裁决继续放在“审阅与定稿”弹窗，维持不可变报告与可变裁决的既有边界。

编辑过程中右栏仍然对应进入编辑时的基础 Revision。栏头必须保持“基于 vN 的审阅”提示，避免用户误以为审阅已经覆盖尚未发布的修改。

## 目录简化

- 阅读状态和编辑状态的目录标题都移除数量数字。
- “第 1 集”“第 2 集”等实际分集编号继续保留。
- 只有一个有效 `document:main` 部分的完整文档不显示目录，内容区全宽展示。
- 多部分文档继续保留普通目录；目录只负责定位，不展示结构化 JSON 或内部字段。

## 组件边界

将当前重复的阅读和编辑结构收敛为一个项目文档工作区，但不把所有逻辑堆进单个组件：

- `RevisionLibraryModal`：负责弹窗生命周期、文档和版本选择、历史加载。
- 文档工作区：负责 `view/edit` 模式、目录选择和导航保护。
- Working Copy 控制器或 Hook：负责创建、恢复、脏状态、保存和发布。
- 剧本正文对照视图：负责精确匹配审阅 Revision、正文/审阅分栏和窄屏标签。
- 审阅分集展示模型：把结构化 `completed/failed` 结果转换成稳定的只读 Markdown 或问题视图，不暴露原始 JSON。

这些组件依赖现有 screenplay service 和 Revision/Working Copy 类型。通用 Markdown 编辑器不感知审阅业务，审阅匹配逻辑也不进入通用 Agent Core。

## 错误与并发处理

- 创建 Working Copy 前重新读取项目 Revision，防止基于已失效状态编辑。
- 保存继续使用 Working Copy Revision 做乐观并发校验；冲突时不覆盖服务器内容，并保留本地文本供用户复制或重新加载。
- 发布候选版本时先完成保存，再以保存返回的 Working Copy Revision 发布。
- 正文对照栏读取审阅失败时只影响审阅栏，不阻止正文阅读和编辑。
- 审阅报告绑定其他正文版本时按“尚无对应审阅”处理，不做模糊回退。
- 关闭弹窗时取消尚未完成的纯读取请求，但不能取消已经提交的保存或发布命令。

## 测试要求

### 审阅领域与后端

- 每个审阅子任务输入包含指定 Revision 的真实分集正文、场景计划和内容摘要。
- 输入缺失时不启动模型，也不产生内容问题。
- `candidate_write` 阶段仍不开放正文读取工具，阶段白名单门禁继续通过。
- 模型输出的 `failed` 字段不能伪造宿主失败状态。
- 单集执行异常只进入 `failedEpisodes`，不进入 `issues`。
- 部分分集失败时其他分集结果保留，但服务端拒绝定稿。
- 失败集重试只能针对同一正文 Revision，成功后产生新的不可变报告。
- 新报告缺少输入摘要或协议版本时不能满足定稿条件。

### 项目文档前端

- 点击“基于此版本编辑”不会出现第二个弹窗，当前工作区原位切换编辑状态。
- 剧本正文编辑时左侧编辑器和右侧审阅栏同时可见。
- 正文版本或分集不匹配时绝不展示其他版本的审阅。
- 分集内切换不触发未保存确认，并保留其他分集本地修改。
- 切换文档、版本、退出编辑和关闭弹窗时，脏状态统一触发三选项确认。
- 保存失败不会关闭编辑器或丢失本地内容。
- 发布成功后退出编辑并选中新候选版本。
- 单篇完整文档不显示目录；多篇目录不显示数量数字。
- 窄屏使用正文/审阅标签，不产生不可用的狭窄双栏。
- 审阅失败、无意见、无对应审阅和正常意见四种状态文案准确。

### 回归门禁

- 审阅裁决弹窗仍是唯一可修改裁决状态的入口。
- 项目文档继续以 Markdown 为默认阅读和编辑表示，不回退到结构化 JSON。
- TypeScript、相关前端单测、后端审阅测试、Agent 架构边界门禁、Web 构建和宽窄屏视觉检查通过。

## 验收标准

1. 审阅第 1 集时，运行输入中包含所选剧本 Revision 的第 1 集正文；内部工具或模型异常不会产生一条“正文不可读”的剧情缺陷。
2. 任一集审阅失败时，用户看到“第 N 集审阅失败”，其他正常问题仍可查看和处理，但不能确认定稿。
3. 在“项目文档 → 剧本正文”选择第 7 集时，左侧展示第 7 集正文，右侧只展示绑定该正文版本的第 7 集审阅。
4. 点击“基于此版本编辑”后不出现第二层弹窗，正文区域直接变为 Markdown 编辑器，右侧审阅保持可见。
5. 修改多个分集后可以统一保存；关闭或切换版本时不会静默丢失未保存内容。
6. 原作分析等单篇文档全宽展示；所有目录标题不再显示内容数量。

## 与现有设计的关系

本设计扩展而不推翻以下既有边界：

- `2026-08-10-screenplay-review-adjudication-finalization-design.md` 中“Agent 软审阅 + 用户裁决 + 用户确认定稿”的状态模型继续有效；本设计新增“审阅分集执行失败”硬门禁。
- `2026-08-10-screenplay-review-panel-layout-design.md` 中审阅裁决通过 CURRENT TASK 入口打开弹窗的设计继续有效；正文对照栏只读，不把裁决操作重新塞回项目文档。
