# PurrTypos Agent 架构改造：十四阶段学习问题与标准答案

> 本文将改造过程中讨论过的问题按阶段重新归类。部分口语问题经过统一措辞，但保留了原本要考察的知识点。每一题均包含标准答案和容易混淆的地方，适合作为 Agent 开发复习材料。

## 总览

| 阶段 | 主题 | 核心能力 |
|---|---|---|
| 1 | 工具契约 | Schema、Handler 与启动路径一致 |
| 2 | 人工审批 | 高风险动作的宿主授权与异步等待 |
| 3 | Planner / To-do / Executor | 计划、步骤和执行权限分离 |
| 4 | 上下文与记忆 | 动态 Token 预算、完整轮次裁剪与冲突处理 |
| 5 | 可观察性 | 使用 `run_id` 还原完整因果链 |
| 6 | 确定性 Planner 评测 | 在开发和 CI 中发现规划回归 |
| 7 | 人工质量评审 | 区分运行正确与回答质量 |
| 8 | 真实模型 Pilot | 在真实适配器与模型组合中发现问题 |
| 9 | Runtime Regression | 把真实事故变成永久回归契约 |
| 10 | 可靠性与恢复 | 终态、取消、阻塞和幂等重试 |
| 11 | 性能与成本 | 定位 Planner、模型、工具和 Schema 成本 |
| 12 | 发布与灰度 | 上线门禁、暂停、拒绝和回滚 |
| 13 | 安全红队 | 把模型和检索内容视为不可信输入 |
| 14 | 架构收口 | 模块边界、运维手册与持续演进 |

## 第一阶段：工具契约

### 问题 1：为什么模型可见的工具 Schema 必须与后端实际注册的 Handler 一致？

模型看到 Schema 后会认为该能力真实存在。如果 Schema 中存在工具，但后端没有 Handler，模型生成的结构化工具调用就会在运行时失败。反过来，如果后端存在未声明的 Handler，它可能绕过模型侧能力清单，形成不可审计的隐藏能力。

正确关系是：

```text
模型可见工具集合 = 后端可执行 Handler 集合 = 已分类 Tool Policy 集合
```

容易混淆点：Schema 是给模型看的说明书，不是后端安全授权。即使集合一致，运行时仍需 allowlist 和 Tool Policy。

### 问题 2：为什么手工维护 Schema 和 Handler 清单会形成潜在风险？

因为一次新增、重命名或删除工具需要修改多个位置。开发者容易只修改其中一处，造成声明与实现漂移。这种错误通常不会在普通单元测试中立刻出现，而会在模型恰好调用该工具时才暴露。

正确做法是从真实注册表生成或检查契约，并在启动时 fail fast。

### 问题 3：为什么测试通过不代表生产启动路径正确？

测试可能直接 import 某个模块，因此顺带触发 Handler 注册；生产启动路径却可能没有 import 该模块。于是测试环境的注册表完整，真实进程的注册表却不完整。

所以需要“全新进程启动测试”：从与生产一致的入口启动一个干净进程，再检查最终注册表。

### 问题 4：全新进程测试会在真实用户使用过程中自动触发吗？

通常不会。它主要属于开发、CI、打包和发布前测试，用来模拟真实启动环境。生产启动时可以运行轻量契约检查，但不应在每轮对话中重复执行完整的全新进程测试。

## 第二阶段：人工审批与异步等待

### 问题 1：为什么高风险工具不能让模型自行决定是否执行？

模型只能表达“想调用什么”，不能成为授权主体。删除、持久化写入等操作必须由宿主 Tool Policy 判断风险，并由用户作出最终批准。

提示词中的“请先确认”只是软约束；真正的安全边界必须位于后端执行器。

### 问题 2：为什么把审批请求放进被阻塞的普通执行队列可能造成死锁？

主执行队列正在等待审批结果，审批事件却排在同一个队列后面。前端收不到审批事件，用户无法作出决定；后端又一直等待用户，形成互相等待。

正确流程是：审批请求通过独立异步事件通道立即发送给前端，主工具协程只挂起当前调用，不阻塞事件派发。

### 问题 3：为什么审批 ID 必须一次性消费？

如果批准可以重放，一次“同意删除 A”可能被再次用于另一时刻或另一操作。安全的审批必须绑定当前 live pending 请求、具体参数和当前进程状态，消费后立即失效；后端重启后也应失败关闭。

## 第三阶段：Planner、To-do 与 Executor

### 问题 1：To-do、Plan 和 Executor 分别是什么？

- Plan 是完成用户目标的有序策略，描述步骤之间的关系。
- To-do 是某次 Run 中可跟踪的具体步骤及其状态。
- Executor 是真正推进步骤的执行机制，可能是模型、工具或人工确认。

Plan 回答“怎么做”，To-do 回答“当前要做哪些步骤、做到哪里”，Executor 回答“由谁、以什么约束执行”。

### 问题 2：计划步骤中的 `suggestedTools` 留空意味着什么？

必须结合 `executor` 解释：

- `executor=model` 且工具为空：这一阶段只允许模型推理或回答。
- `executor=tool` 且工具为空：这是无效计划，因为工具步骤没有可执行能力。

不能把空集解释成“允许所有工具”。在安全系统中，空 allowlist 就应表示不允许任何工具。

### 问题 3：为什么既要限制整份计划的工具，又要限制当前步骤的工具？

整份计划可能需要读、分析、写三类能力，但读取步骤不应提前获得删除或写入权限。当前步骤 allowlist 能阻止模型跳过分析流程直接执行后续高风险动作。

### 问题 4：为什么模型可见的 Schema 与后端实际允许执行的工具必须分开？

Schema 是能力说明；后端 allowlist 是执行授权。模型可能生成未展示、过期或伪造的调用，所以后端必须独立验证。安全不能依赖“模型没有看到，因此不会调用”。

## 第四阶段：上下文与记忆预算

### 问题 1：独立计算 Token 用量与独立分配窗口预算有什么区别？

独立计算只是知道历史、记忆、章节和工具 Schema 各自用了多少 Token；独立分配预算则是在总窗口约束下，决定本轮每部分最多可以使用多少。

前者是计量，后者是资源决策。只有计量而没有预算，仍可能整体溢出。

### 问题 2：为什么不能每轮都把全部历史、记忆和章节一股脑塞给模型？

上下文窗口有限，输入越多还会产生注意力稀释、噪声增加、成本上升和幻觉。极端情况下，历史占满窗口会让真正重要的记忆或章节完全无法注入。

目标不是“最多上下文”，而是“在预算内保留最相关、最可靠、最完整的上下文”。

### 问题 3：动态预算应该如何分配？

先扣除不可争抢的部分：系统提示、输出预留、当前工具 Schema。剩余预算由历史、长期记忆和关联章节根据本轮需求申请。分配时考虑：

- 用户是否明确选择某些上下文。
- 当前任务是问答、分析还是多步 Agent。
- 信息的重要度、相关度、置信度和时效性。
- 每个区域的最低保障与最大上限。
- 某区域未使用的预算是否可借给其他区域。

例如记忆获配 8K 但只用 2K，剩余 6K 应允许关联章节或历史借用。

### 问题 4：为什么历史裁剪应以完整对话轮次为单位？

一轮通常包含用户问题、助手回答、工具调用及工具结果。单独删除某条消息会破坏因果关系，例如保留工具结果却删除对应调用。完整轮次裁剪能维持协议与语义完整性。

### 问题 5：为什么还要区分整份计划工具和当前步骤工具？

上下文预算解决“模型看到多少”，步骤工具约束解决“模型此刻能做什么”。前者影响回答质量，后者属于执行安全，它们不能互相替代。

### 问题 6：如何区分记忆的“取代”与“矛盾”？

取代表示新事实明确声明旧事实已经失效，例如“角色年龄从 18 岁改为 20 岁，以新设定为准”。矛盾表示两条事实无法同时成立，但缺少明确的版本关系或用户决定。

- 明确、有来源、带替代语义：可标记 `supersedes`，旧记忆归档但保留审计记录。
- 无法确定哪条正确：标记 `contradicts`，保留双方并请求用户判断。

不应因为发现冲突就静默删除任意一条记忆。

### 问题 7：为什么本地估算没有溢出，上游模型仍可能返回 context overflow？

本地 Tokenizer 可能与供应商实际 Tokenizer 不一致；供应商还可能加入隐藏系统消息、工具包装和推理开销。因此本地预算必须保留安全余量，并把上游溢出作为可诊断失败，而不是假设估算绝对准确。

## 第五阶段：可观察性与 Run Trace

### 问题 1：为什么 Trace 必须绑定 `run_id`？

一次 Agent 请求包含 Planner、上下文、多个模型轮次、工具调用、审批和终态。没有统一 `run_id`，这些事件无法可靠串成同一条因果链，也无法根据用户提供的编号回溯问题。

### 问题 2：为什么 `blocked` 不能简单等同于系统失败？

`blocked` 可能表示等待用户批准、用户拒绝高风险操作、缺少业务条件或工具暂时不可用。系统失败只是其中一种可能，而且通常应使用 `failed` 表示。混用会污染可靠性统计和恢复策略。

### 问题 3：为什么更多工具和更多上下文不一定让模型回答更好？

工具与上下文只是影响因素。更重要的是它们是否准确、相关、无噪声且与当前步骤匹配。无关工具会增加误调用概率；过量上下文会稀释核心事实，反而增加幻觉。

## 第六阶段：确定性 Planner 评测

### 问题 1：这一阶段的目的是什么？

用固定输入、固定工具集合和确定性检查，验证 Planner 是否生成有效结构、必要工具、禁止工具以及安全的步骤顺序。它将“看起来计划还行”变成可重复判断。

### 问题 2：Planner 评测会在每轮真实对话中运行吗？

不会。它主要在开发、CI、模型升级和提示词修改后运行。真实对话只执行正常 Planner；把完整评测套件放入每次对话会增加成本和延迟。

### 问题 3：为什么不能只检查最终回答是否正确？

相同最终文本可能来自安全流程，也可能来自越权、漏读或错误工具顺序。Planner 评测关注中间结构和行为契约，能在真实副作用发生前发现问题。

## 第七阶段：人工质量评审

### 问题 1：为什么运行测试通过仍不能证明 Agent 回答质量高？

运行测试只能证明状态机、工具权限和协议正确。回答可能仍然没有依据、遗漏用户目标、不可执行或文风不合适。因此内容质量需要独立评审。

### 问题 2：为什么人工评审要使用固定 Rubric？

固定维度使不同 Run、不同模型和不同评审者的评分具有可比性。本项目使用事实与上下文一致性、任务完成度、可执行性、安全校准和写作适配度等维度。

### 问题 3：人工评分能代替自动测试吗？

不能。人工评分适合判断语义质量，但成本高、主观性强；自动测试适合检查确定性安全和协议。二者分别回答“系统是否正确运行”和“结果是否真正有用”。

## 第八阶段：真实模型 Pilot

### 问题 1：为什么有了单元测试和确定性评测，还需要真实 Pilot？

真实模型会暴露供应商参数兼容、流式协议、工具调用格式、推理模式、延迟和多轮组合问题。这些问题通常无法由 Fake Model 完整模拟。

### 问题 2：为什么 Pilot 要使用固定案例、前置条件和观察点？

否则每次测试都换问题、换数据，结果无法比较。稳定案例让不同版本、模型和供应商在相同条件下接受检查。

### 问题 3：为什么 Pilot 必须记录 `run_id`？

当表面现象是“不调用工具”时，真正原因可能在 Planner、Schema、供应商降级或状态机。`run_id` 能把人工观察与后台 Trace 对齐。

## 第九阶段：Runtime Regression

### 问题 1：为什么真实事故修复后还要转成永久回归案例？

只修代码不能保证以后重构、换模型或换供应商时问题不再出现。将事故最小化成固定输入、预期 Trace 和终态，才能让 CI 永久守住该行为。

### 问题 2：为什么 Planner 出错时应该 fail closed，而不是静默生成一个简单计划？

静默兜底会让系统看似继续运行，却失去原本的步骤与权限约束。用户可能看到错误结果，后端也难以判断真实 Planner 已失败。显式失败更安全、更可诊断。

### 问题 3：供应商不支持 `tool_choice=required` 时，为什么降级到 `auto` 仍不能取消后端 allowlist？

`required/auto` 是供应商请求参数；allowlist 是宿主授权边界。为了兼容供应商可以改变请求方式，但不能扩大后端允许执行的工具集合。

### 问题 4：为什么连续多个模型步骤有时可以由一次最终回答完成？

`analyze → review → answer` 可能只是逻辑阶段，不一定需要三次独立模型请求。如果没有待执行工具和必须分段的结构，一次完整回答可以覆盖多个模型步骤，减少轮次和成本；但仍需由 Run Controller 正确推进状态。

## 第十阶段：可靠性与失败恢复

### 问题 1：为什么客户端断开后必须把 Run 持久化为 `canceled`？

如果只停止流式连接而不更新数据库，Run 会永久停留在 `running`，形成僵尸任务。明确的 `canceled` 能反映用户中止，而不会被错误统计成系统失败。

### 问题 2：为什么读取工具通常可以重试，而写入工具不能盲目重试？

读取通常幂等，多执行一次不改变状态。创建、修改和删除可能重复产生副作用，因此必须使用幂等键、执行记录、事务或人工确认后再决定是否重试。

### 问题 3：为什么 `declined` 与 `failed` 必须区分？

`declined` 表示用户正常拒绝授权，是产品流程的一部分；`failed` 表示模型、工具、网络或系统异常。混用会把正常安全决策错误统计成系统故障。

## 第十一阶段：性能与成本治理

### 问题 1：为什么性能预算超标应产生 `warn`，而不是把正确完成的 Run 标成 `failed`？

性能超标说明运行慢或贵，不代表结果错误。若标成失败，系统可能自动重试并进一步增加成本，还会混淆正确性指标与效率指标。

### 问题 2：为什么供应商能力缓存键必须包含 Provider、Base URL、Model 和 Thinking Mode？

同名模型在官方端点、代理端点或不同思考模式下可能支持不同参数。缓存键不完整会把一个端点的能力结论错误应用到另一个端点。

### 问题 3：为什么优化成本时应先减少失败请求、重复轮次和无关 Schema，而不是直接裁剪上下文？

前三者是不产生业务价值的纯浪费；上下文承载任务事实。优先消除无价值成本可以同时提升速度和稳定性，而盲目裁剪上下文可能降低正确率。

### 问题 4：这一阶段在真实使用中如何体现？

第一次发现某模型不支持 `required` 后，后续请求直接走兼容路径；诊断中还能分别看到 Planner、模型、工具和 Schema 成本。普通用户感受到的是更少重复失败和更低等待，开发者获得的是可定位的性能数据。

## 第十二阶段：发布门禁与灰度回滚

### 问题 1：为什么必须在 Run 创建时保存版本和灰度组？

版本属于运行发生时的历史事实。如果诊断时才读取当前应用版本，应用升级后旧 Run 会被错误归因到新版本，污染灰度统计。

### 问题 2：`hold`、`reject` 和 `rollback` 分别代表什么？

- `hold`：证据不足或性能退化，暂不扩大范围。
- `reject`：上线前已经证明候选版本不合格。
- `rollback`：候选版本已经灰度，但相对基线发生严重退化，应恢复基线。

### 问题 3：为什么 P95 延迟退化通常只需要 `hold`，工具越权一次却应触发回滚？

延迟属于效率指标，需要结合样本和外部状态判断；工具越权代表安全不变量失效，可能造成真实副作用。安全不能用“99 次正常抵消 1 次越权”的平均思维处理。

## 第十三阶段：安全威胁建模与红队测试

### 问题 1：为什么把章节和记忆标记成“不可信数据”，仍然不能替代后端工具权限校验？

不可信数据封装只能降低模型把素材当指令的概率，不能从数学上保证模型永不受 Prompt Injection 影响。模型输出始终是不可信建议。真正的安全必须由后端 allowlist、Tool Policy、对象归属和人工审批保证。

### 问题 2：为什么工具参数 JSON 解析失败时必须拒绝执行，而不能退化成空对象？

某些工具存在默认参数。非法 JSON 如果退化成 `{}`，Handler 可能使用默认书籍、默认章节或默认操作继续执行，使“解析失败”变成“执行了另一件事”。安全系统应 fail closed。

### 问题 3：为什么既要绑定宿主 `bookId`，又要检查目标对象 ID 的书籍归属？

只固定 `bookId` 仍不足以防止模型传入另一书籍的全局对象 ID。后端必须验证 `memoryId`、`characterId`、`entityId` 等目标确实属于当前书籍，才能阻止跨租户/跨作品对象访问。

### 问题 4：为什么单轮工具调用数、参数大小和结果大小都需要限制？

总轮数限制只能防止无限循环，不能阻止模型在单轮生成数百个调用或超大参数。分层限制能防止 CPU、数据库、审批队列和上下文窗口被一次请求耗尽。

## 第十四阶段：架构收口与工程化交付

### 问题 1：为什么单次 Run 诊断、发布门禁和灰度回滚必须是不同层次的决策？

- Run 诊断判断某一次执行发生了什么。
- 发布门禁判断候选版本是否有资格进入小范围真实环境。
- 灰度回滚比较候选组与基线组，判断是否扩大或撤回。

单次成功不能证明版本整体可靠，版本整体平均成功也不能解释某次具体事故。

### 问题 2：新增工具时，Schema、Planner allowlist、Tool Policy 和 Handler 分别负责什么？

- Schema：告诉模型工具名称、用途和参数格式。
- Planner allowlist：限制当前计划或步骤允许请求哪些工具。
- Tool Policy：由宿主定义 read、propose、confirm 风险和审批要求。
- Handler：执行业务逻辑，并验证对象归属和参数语义。

四层缺一不可，任何一层都不能独自代表完整安全性。

### 问题 3：为什么生产事故修复后必须转成永久回归案例？

事故说明原有测试网存在盲区。只修当前代码会让团队在未来重构中再次踩坑；把最小复现、预期终态和安全检查固化为 Runtime Regression 或 Security Red Team Case，才能让系统从事故中积累能力。

### 问题 4：架构文档和运维手册为什么也是系统的一部分？

代码只能表达当前实现，无法完整说明状态语义、信任边界、故障处理和发布原则。没有文档，新开发者容易重新合并已经刻意分开的概念，使架构随人员变化而退化。

## 最终知识框架

一个可靠 Agent 可以概括为以下公式：

```text
可靠 Agent
= 不确定的模型推理
+ 确定性的宿主状态机
+ 最小化工具授权
+ 动态而有边界的上下文
+ 一次性人工审批
+ 可回溯 Run Trace
+ 自动回归与人工质量评审
+ 灰度发布和安全红队
```

最核心的原则是：

> 模型负责提出计划、生成内容和请求能力；宿主负责决定什么可以执行、记录实际发生了什么，并在证据不足或边界失效时停止系统。
