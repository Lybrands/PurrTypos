## 1. 目标、基线与范围

将来源蒸馏生成的写作技法、技法库中人工创建或导入的技法、写作方案，以及小说写作时的使用方式，统一为一条完整链路：

> 来源观察 → 提炼并组织技法文件 → 编辑草稿 → 保存可用版本 → 组合方案或直接选择 → 从入口按需读取 → 用于写作。

0.6 的现有代码已提交为 `a3835a9`，合入主分支后的基线为 `590f17e`；`main`、`feat/1.0.0`、`release/1.0.0` 已同步到该合并提交。本计划的新能力在 `feat/1.0.0` 开发，不继续扩展 0.6。

本计划替代 [旧写作方法与小说续写计划](2026-08-27-writing-methods-and-novel-continuation-implementation-plan.md) 中与写作技法、方案、蒸馏和技法使用相关且发生冲突的设计。原作只读、冻结来源和独立续写仍保留；其工作台、资料继承和默认技法行为按 2026-09-08 扩展继续开发。旧文档是历史记录，不能用其“候选必带方案”等约定覆盖本次决定。

本次范围包括：内容契约、本地文件存储与版本、技法库编辑、方案组合、授权与本轮选择、Agent 读取、来源蒸馏、导入导出与备份，以及相关旧结构清理。第一版不建设云端服务、多人协同或任意外部目录的实时技法库；不扩大到剧本业务，也不预设需要修改独立 PurrA 仓库。

### 1.1 两条同等重要的工作线

| 工作线 | 需要解决的问题 | 独立交付 |
| --- | --- | --- |
| A：业务实现 | 技法如何存储、编辑、形成版本、组合方案、授权并用于写作 | 文件与业务契约、存储和接口、管理界面、Agent 读取及运行记录 |
| B：生成规范与内置提示词 | 模型如何从来源提炼写法、判断保留什么、组织单文件或多文件，并写出可执行且协调的技法 | 生成规范、内置提示词、质量示例与反例、验证样本及实际生成结果 |

两条线共同使用一个技法产物契约，但分别验收。能保存文件不代表生成的内容可用；提示词生成的文字看起来合理，也不代表系统能从入口正确读取并用于写作。

B 线从内容标准与示例开始，可以与 A 线的存储和界面工作并行，不等业务实现结束后才补提示词。文件和工具契约确定后完成接入，最后联合验证“生成 → 保存 → 按需读取 → 用于写作”。

P0 的详细交付统一关联在此，不复制维护多份契约：

- [行为与数据契约](2026-09-07-writing-techniques-p0-contracts.md)：模式、授权、入口元信息、文件操作、版本、结果状态及保存恢复。
- [旧结构退役清单](2026-09-07-writing-techniques-legacy-retirement.md)：真实调用者与数据范围、保留规则、历史运行和备份处理。
- [生成与独立使用评估清单](2026-09-07-writing-techniques-evaluation.md)：具体文稿、观察、证据边界、使用任务及通过条件；实际执行状态见[实施验收记录](../validation/2026-09-07-writing-techniques-implementation.md)。

## 2. 已确认的产品与内容规则

### 2.1 统一术语

| 概念 | 职责 |
| --- | --- |
| 写作技法 | 一个可以独立使用的写作方法，以入口及可选辅助文件保存 |
| 写作方案 | 组合多个写作技法，并可说明它们的分工、配合与取舍 |
| 写作技法库 | 管理人工创建、导入和蒸馏生成的写作技法及方案 |
| 小说与对话 | 通过授权、绑定和本轮选择使用技法或方案 |

用户界面与项目讨论统一使用“写作技法”“写作方案”，不增加“技法包”“low skill”等产品对象。`SKILL.md` 只是入口文件名。现有英文符号、API 名称及路由如何统一，在契约阶段确定；不要仅替换界面文字而留下相互不一致的业务概念。

### 2.2 主入口与内部文件

- 每个写作技法有且只有一个主入口，约定为 `SKILL.md`。
- 只有一个入口文件，就是完整、合法的技法；辅助文件和目录全部可选。
- 不强制“总览、文风、节奏、对白”等固定文件，也不要求固定正文标题或章节。
- 作者决定文件命名、划分、相互引用及组合方式。作者既可以是用户，也可以是蒸馏 Agent。
- 使用技法必须从入口开始，随后根据任务与文件中的说明读取必要内容。
- 单文件入口可以承载完整写法；多文件入口需要能指导使用，不能只有一串文件名。
- 入口元信息中的名称和简短用途需要说明解决什么写作问题、何时适用，帮助区分相近技法；具体字段格式按应用契约确定。
- 正文与必要辅助文件应能被未读过来源、未参与分析的写作者独立使用，不依赖“沿用原文处理”“参考前面的分析”等外部上下文。
- 系统识别入口、提供包内文件访问并验证引用边界，不替作者规定内容结构。引用不等于自动递归加载全部文件。
- 一个技法包含多个文件，不代表产生了多个独立技法或一个写作方案。
- 分析生成、手动创建和导入后编辑，使用相同的内容结构与版本规则。

### 2.3 写作技法提炼什么

聚焦可以实际使用的写法，例如叙述视角、语言风格、节奏、铺垫、信息揭示、人物表现、对白、描述和情绪处理。这些是观察方向，不是必须凑齐的类别。

正文说明“怎样写”，必要时说明成立条件和取舍。先删除不相关内容、合并重复机制，再决定是否拆文件。删除不会改变这份技法使用方式的泛泛建议，保留理解和执行所必需的前提，即使它属于常见写作知识。不能把“节奏紧凑”等效果评价直接当成可执行技法，也不能把单次现象或推测的作者意图写成普遍规律。

不强制为每个技法补齐适用情境、边界、步骤检查、失败清单和整套检查表。必要说明可以保留，但由内容决定。部分观察成立时，保留有依据且可独立使用的部分，不因其他观察不足而否定全部结果。没有可用机制时，允许形成“材料不足”的结果，不生成占位技法或硬凑完整体系。

来源故事、事实、观察证据与分析记录留在来源分析体系，通过关联入口查看，不自动堆入技法正文。提炼可复用的写法，不搬运来源人物、专有设定和情节作为新创作模板。

正文中的限制优先写成影响创作选择的使用条件；来源覆盖、证据缺口和分析可信度说明单独保存。保留必要的使用边界，但不让每个文件反复解释“材料没有证明什么”。

默认移除“迁移试写 → 修订 → 再次试写 → 迁移评估”的强制链路及入库门槛。保留必要的结构检查和内容复核，不能把取消迁移试写解释为取消所有质量检查，也不能继续把试写报告作为默认交付物。

### 2.4 三个贯穿全链路的控制点

| 控制点 | 设计约束 | 验收证据 |
| --- | --- | --- |
| 内容冗余 | 先筛选和去重；按内容关系拆分；不按固定分类、来源章节、观察条数或字数机械拆文件 | 简单来源能形成简洁单文件；复杂来源的每个辅助文件有独立用途；多文件情况下，入口不重复辅助文件的完整正文 |
| 实际读取量 | 引入从入口开始；按任务及作者说明访问辅助文件；不自动拼接全包或全库 | 检查真实模型调用输入和读取凭据，能确认相关文件被使用、无关文件没有被加载 |
| 整体一致性 | 作者负责内容协调；系统保证引用有效、版本完整和读取稳定；方案考虑组合后的重复与冲突 | 包内引用、组合规则与固定版本回归；不混用入口和辅助文件的不同版本 |

## 3. 写作方案与小说使用方式

### 3.1 方案组合

方案保存名称、用途、所引用技法的准确版本，以及可选的组合说明。方案引用完整技法，不直接绑定内部文件。组合说明可描述分工、触发条件和取舍，不强制复杂规则模板。

不能假定把多个技法放在一起就自然协调，也不采用“后加入的一律覆盖前者”规则。数据层拒绝同一技法的多个版本，自动候选与手动项冲突时跳过自动项；写法上的条件与取舍由方案说明和本轮要求协调，确实无法同时满足时向用户说明具体冲突。完整规则见 P0 契约第 1 节。

生成一个技法无需自动创建一个方案。方案是用户实际需要组合技法时使用的对象，不再充当单个生成结果的必备容器。

### 3.2 一个模式配置，始终保留手动入口

输入框下方工具区提供“技法使用：自动选用 / 仅手动指定”，同时保留添加写作技法或方案的入口。用户可以手动上传技法，或选择已有技法、方案；具体控件文字与默认值见第 10 节。

| 行为 | 自动选用 | 仅手动指定 |
| --- | --- | --- |
| 上传或手动选择技法、方案 | 支持 | 支持 |
| 搜索已经授权的技法、方案 | 允许 | 不执行 |
| Agent 按任务补充选择 | 允许，只在授权范围内 | 不允许 |
| 本轮有效选择为空 | 可以自动选择，也可以不使用技法 | 普通写作，不隐式注入技法 |

续写新增可见的来源技法默认选择，默认模式仍为仅手动指定。默认项与本轮临时项共同组成有效选择；用户明确取消后不得自动补回。其持久化、授权与入队行为见续写继承扩展，不能沿用“发送后清空全部选择”的旧实现。

手动指定的内容优先，Agent 不能擅自替换或忽略。自动选用不等于注入全部已授权内容。仅手动模式必须在后端检索和上下文组装处生效，不能只是隐藏前端按钮；旧“主方法常驻”也不能绕过这一限制。

授权决定“可访问什么”，模式决定“能否主动寻找和选择”。打开自动模式不扩大授权；导入或上传不自动授予以后长期自动选用的权限。

手动选定技法后，读取它的入口及必要辅助文件属于正常执行；手动选定方案后，可使用其明确包含的技法，不算 Agent 自行补充技法。方案展开仍要经过宿主准入，不能利用成员引用越过权限。

### 3.3 从发现到实际读取

1. 宿主确定本轮模式、手动选择、可用授权范围和准确版本。
2. 自动模式可搜索授权目录的名称、用途等轻量信息；这些描述要能说明实际能力和适用时机，不能统一写成“提升写作水平”。仅手动模式不发现其他技法或方案。
3. 确定采用的技法后，先读取各自入口；目录摘要不能代替入口。
4. 按作者说明和任务读取必要辅助文件，处理必读依赖、重复访问、断链及循环引用。
5. 在现有上下文预算内完成写作，并记录实际使用的版本、文件及选择来源。

技法是服务当前任务的创作参考。用户指定的内容、段落形式、情绪落点与结束位置优先；示例的篇幅和结构不能替代本次输出要求。交付前只核对并修正当前正文的遗漏与冲突，不增加独立模型阶段。正式上下文与独立使用验收共用 `WRITING_TECHNIQUE_USE_POLICY`，验收只补充读取工具说明，不另写一套任务遵循规则。

明确的一段小说正文请求由 Writing 响应校验检查段落数量；不符合时使用既有响应修复路径，只修正正文形式，不重做来源分析或技法生成。代码、多段及多个写作任务不启用此保守识别规则。情绪含义等语义要求仍与格式检查分开验收。

读取受到本轮授权和固定版本限制，文件中的内容不能扩大工具权限或自行绑定、升级、解绑技法。固定版本也不代表永久授权；撤销后下一次受影响调用停止，恢复不能绕过旧授权代次，具体准入与在途边界见 P0 契约第 2 节。

实现建议（依据现有架构）：复用当前 Run 绑定与上下文证据体系，绑定快照回答“本轮允许什么”，实际读取凭据回答“模型收到了什么”；不新建一套平行的业务执行账本。文件级凭据应能关联技法版本、相对路径和内容摘要。

界面展示手动选择项；运行结果中简洁展示实际采用的技法、方案及“手动指定 / 自动选用”来源。不得把仅搜索到、列在目录中或未成功读取的内容显示为已使用。

## 4. 本地文件存储与版本

### 4.1 数据的正式来源

| 数据 | 正式存储 | 约束 |
| --- | --- | --- |
| 技法入口、辅助文件、名称与用途等描述 | 本地文件，描述放在入口头部元信息 | 不在数据库维护第二份可编辑正文 |
| 方案组合说明、成员版本引用 | 本地方案文件 | 引用稳定 ID 和版本，不依赖显示名称或绝对路径 |
| 技法、方案的可用版本 | 本地完整快照 | 已形成的版本不可原地修改 |
| 小说绑定、授权、本轮模式等应用状态 | 本地 SQLite | 是正式业务数据，不能视为可随意重建的缓存 |
| 列表、搜索索引 | 可重建缓存 | 从文件重建不改变授权、不复活删除项 |
| 来源分析与运行证据 | 现有来源分析和 Run 体系 | 关联技法文件版本，不建立另一套可编辑技法正文 |

SQLite 本身是本地存储。选择文件承载内容，是为了支持多文件组织、直接编辑、导入导出和备份，不是因为离线场景不能使用数据库。

### 4.2 建议目录布局

以下是便于理解的逻辑目录示例；P0 契约第 4 节定义了支持编辑恢复的文件代次和正式管理布局。根目录沿用 `PURRTYPOS_DATA_DIR`；Electron 已向后端传入应用 `userData` 目录。

```text
应用数据目录/
└── writing-library/
    ├── techniques/
    │   └── 技法ID/
    │       ├── draft/
    │       │   ├── SKILL.md
    │       │   └── 可选辅助文件或目录
    │       └── versions/
    │           └── 版本ID/
    │               ├── SKILL.md
    │               └── 对应版本的辅助文件或目录
    └── schemes/
        └── 方案ID/
            ├── draft.json
            └── versions/
                └── 版本ID.json
```

作者维护草稿投影中的作者文件，管理目录和版本由应用负责。单文件技法不因此被要求编写额外清单。P0 已确定入口 YAML 的 name/description、Markdown 相对引用、Markdown/TXT 辅助文件与 JSON 方案格式，详见 P0 契约第 3 节。

### 4.3 保存与使用

- 逐文件编辑或生成进入草稿；不完整草稿不能进入自动选用范围。
- 保存可用版本时形成完整快照，方案和小说引用准确版本；已有绑定不跟随草稿自动变化。
- 一次写作读取同一技法版本，不能入口用新版本、辅助文件用旧版本。
- 文件系统与 SQLite 不共享事务；实施需设计临时写入、完整性校验、提交顺序和中断恢复，避免出现“数据库已绑定但文件没落盘”的可见状态。
- 并发编辑、外部修改、缺失文件、同 ID 冲突、路径越界和符号链接等情况需要明确处理，不把任意宿主文件路径交给 Agent。
- 第一版使用应用管理的固定目录，支持打开所在目录和导入导出。任意外部目录监听、实时同步不纳入第一版。

### 4.4 导入、导出、删除与备份

导入内容复制到应用管理范围，保留文件关系；本轮使用、存入技法库、长期自动选用分别处理。导出方案需支持携带所引用的技法版本，导入后不能因旧机器绝对路径失效。导入格式及冲突选项见第 10 节。

备份与恢复同时覆盖数据库业务状态和技法、方案目录，校验恢复后的引用。新结构日常从库中删除采用归档语义，保留被引用版本；首版不自动回收历史版本。临时上传、在途保存和备份一致性详见 P0 契约第 4、5、8 节。

## 5. 生成规范、内置提示词与蒸馏链路

### 5.1 本次核对的现有约束

- `backend/domains/writing_distillation.py` 强制适用情境、边界、步骤的 action/rationale/check、失败清单与检查表，并通过 `render_skill` 输出单篇 Markdown。
- `backend/domains/novel_analysis_prompts.py` 的共享指引同样要求步骤、检查标准及新场景试写。只改最终蒸馏提示词会留下相互冲突的上游指令。
- `backend/domains/novel_analysis.py` 的计划构建固定加入初次试写、修订、再次试写和迁移评估；工具、执行器、保存校验和界面共同依赖这些结果。
- `backend/application/writing_method_candidates.py` 要求迁移复核通过，保存一份正文并自动创建候选方案。
- 来源提取与归并提示目前限制最多六条技法观察。需评估是否丢失不同的有效写法，不能只改最终输出格式，也不能未经评估直接取消所有上游限额。
- `backend/domains/writing/method_resolution.py` 当前选中方法后读取整份正文；支持目录界面本身不会改变模型实际输入。

### 5.2 目标生成行为

蒸馏使用来源支持的写作观察与用户关注点，筛选、合并并提炼可执行写法，再决定单文件或多文件组织。不得把先生成的大长文按字数切割当作多文件创作。

Agent 需要能建立技法草稿、创建入口及辅助文件、读取已生成内容、修改文件和引用，并提交完整结果。支持多次调用完成，沿用现有持久任务、产物、取消和恢复能力，不强迫所有文件塞入一次模型回答。

完整提交前检查入口、文件路径、引用和产物版本；内容复核关注来源支持、具体可执行性、重复与冲突。入口必须足以指导后续使用。具体执行步骤由任务规模和现有 Agent 生命周期决定，本文的能力要求不等于新增一条固定多轮模型流水线。

成功后以相同技法结构交给用户查看、编辑和保存，来源证据保持关联，同时保存来源版本与分析结果的技法归属。生成本身不自动绑定既有小说或授权长期使用；从来源创建续写时，为目标作品初始化可用技法的固定版本默认选择与相应权限。无需默认生成方案、试写对照或迁移评估报告。

P0 确定首版每次来源分析产出零个或一个技法，单个技法可包含多个文件；使用 `generated | insufficient_material` 区分成功生成与正常材料不足。材料不足时分析仍可保存，不能因没有技法而反复报错。文件草稿操作、完整 seal、发布和结果引用分别定义，见 P0 契约第 5–7 节。上游观察采用按机制去重与预算化分批保留，不再用固定六条作为语义截断；资源预算仍须保留。

### 5.3 生成规范是独立交付，不只是格式说明

应用需要内置一套指导模型编写技法的生成规范和提示词，不能仅要求“总结写作风格”或“生成 SKILL.md”。其中必须覆盖：

| 规范内容 | 要指导模型作出的判断 |
| --- | --- |
| 来源理解 | 区分具体文本选择、可观察效果和解释；结合来源范围，不把推测当事实 |
| 提炼与取舍 | 把观察转为写作时可执行的处理方式；保留有辨识度的机制及执行必需的前提，删除重复、无助于使用的泛泛建议和无关内容；部分有依据时保留成立部分 |
| 名称与用途 | 简洁说明解决什么写作问题、何时适用，帮助用户和自动选择过程区分相近技法；具体元信息格式由宿主契约确定 |
| 文件组织 | 判断哪些内容应连贯表达、哪些可按任务独立读取；能单文件完成时不额外拆分 |
| 入口编写 | 单文件入口承载完整技法；多文件入口说明共同规则、必需依赖、按需读取条件及配合方式 |
| 正文编写 | 面向未读过来源、未参与分析的写作者，用明确的写作动作、信息安排和取舍说明“怎么写”；必要时使用简短原创示例，不用来源情节充当创作模板 |
| 边界与证据 | 正文保留影响使用的条件；来源覆盖、证据不足和分析可信度单独保存，不把技法写成研究报告 |
| 自检与修订 | 检查空泛、重复、互相冲突、来源不足和引用问题，直接修订草稿；不要求输出完整自检报告 |
| 交付方式 | 按应用提供的文件与工具契约提交完整技法，来源关联独立保存，不混入方案或迁移试写交付物 |

以上是生成时应遵守的质量要求，不是每份技法必须包含的固定章节，也不是等量的模型调用。格式规范与内容自由度要分开：入口和文件提交必须可校验，正文结构由作者决定。

### 5.4 内置提示词的组织与接入

区分两种指引：应用内置的生成提示词指导模型“怎样编写技法”；生成出来的 `SKILL.md` 指导后续写作模型“怎样使用这一技法”。前者的生成流程、工具协议和自检要求不应自动复制进后者。

内置提示词建议按职责维护，由实际任务组合使用：

1. **共同生成规范**：第 5.3 节的内容目标、提炼判断、文件组织、入口规则和质量标准。
2. **来源任务输入**：已校验观察、来源范围、用户关注点、必要的来源证据或只读访问方式；明确已观察内容和证据不足部分。小说与文案共享技法产物结构，来源差异通过输入处理，不要求文案先填小说人物、剧情模板。
3. **文件与工具契约**：准确的入口约定、元信息、相对路径、可用文件操作和提交结果。由宿主提供真实契约，不让模型猜接口或虚构已写入文件。
4. **必要的局部修订指引**：输入真实缺陷与相关草稿，修改受影响内容并检查其依赖，不为每次生成额外安排一整套试写和评估调用。
5. **质量示例**：用少量匹配任务的示例解释抽象程度、入口写法和合理拆分；用于指导质量，不要求照抄标题、题材或目录。

共同生成规范应有单一维护位置，来源提取、聚合、生成、局部修订、最终交付指引不得相互矛盾。装配时合并重复约束，避免每一层都再次注入同一套说明。P0 指定在 `backend/domains/writing_technique_prompts.py` 集中维护并通过装配函数使用；该模块已创建并接入生成单元，生成行为不分散硬编码进前端和路由。

提示词只包含可执行的任务、内容、工具和输出要求，不写对话历史、修复经历、无实际约束的角色头衔或自我评价。保留提示词版本或内容摘要与对应 Run 的关联，便于复现和比较实际结果。

依据 `skill-creator` 的复核原则，只保留能改变生成决策或保证交付正确的指引。把重复的“具体、去重、不套模板”等要求合并到各自职责处；明确唯一入口、合法文件引用等必要约束，其余开放式写作问题提供判断依据，不增加固定操作顺序。借用其简洁、准确发现和渐进读取原则，不引入 Codex 专用的配置目录或命名限制。

### 5.5 核心生成提示词草案（复核修订版）

以下为当前 v1.8 核心生成指引，通过 `writing_technique_prompts.py` 与文件工具契约装配接入。v1.8 完成两遍静态审视，收窄硬约束与原创示例的措辞，并明确提交字段用途；未增加模型阶段。既往真实 Provider 结果属于对应历史版本，不能作为 v1.8 的质量或成本验收。详见 `docs/validation/2026-09-08-writing-technique-prompt-review.md` 的复审记录。

```text
为未读过来源的写作者提炼可独立使用的写作技法。依据来源的具体文字安排和用户关注点，说明一种值得尝试的写法，不制定写作规范。

先核对待采用的观察与所附原文上下文。观察中的术语、归因与效果判断不自动成立；直接描述原文实际怎样安排动作、语言、信息与情绪，不能证实的解释舍弃。保留相互配合的处理，合并重复观察，不追求类别齐全，不必采用全部观察。

正文的核心是：在怎样的创作需要下，可以怎样写。用具体但可调整的建议帮助写作者选择；原文采用的局部手段，不限制新作品的其他写法。遵守用户的创作要求与宿主的文件、工具契约，不把来源中的局部写法推导为强制写作规则。不要把示例的句长、数量、先后顺序或出现过的表达固化成规则，也不要从某种表达未出现推导禁止使用它。适用条件只说明这项写法何时有帮助，不凭空增加环境、身份或情绪前提。不同模式按用户需要说明如何选用，组合方式由新作品的任务决定。

只保留改变实际写作选择的内容。结构由写法决定，不要求目标、做法、条件、取舍等固定栏目；不为填满栏目推导必然效果或损失。需要举例才给简短原创例子，另设情境展示写法，不复述来源情节或仅替换人物、物件名称。来源观察和证据说明独立关联，不写进技法正文，不加入迁移试写任务。

SKILL.md 是唯一入口，按宿主契约提供准确名称与简短用途。一个文件能讲清时在入口写完；辅助内容具有独立使用或按需读取价值时才拆分。入口说明各辅助文件的读取条件与必要配合，使用真实存在的相对链接；不能只列目录或重复全文。相互依赖的内容保持连贯，不能按来源章节或观察数量机械拆分。

提交前只核对正文是否忠于材料、能独立使用、没有把可选建议写成无依据的要求，修正后提交，不另起分析或试写。部分观察有依据时交付成立部分，完全没有可用写法时提交材料不足，不补占位内容。路径、文件和版本合法性由工具处理；收到错误后只修复指出的问题。
```

这份草案还需通过示例校准“具体到什么程度”和“何时拆分”，并与实际生成输入、输出预算、恢复和文件提交契约联合调整。不能只润色词句而保留旧的强制正文 schema。

### 5.6 示例与质量验证

生成提示词的质量需要样本支持，不能以“输出符合 JSON”“文件能打开”或模型自评通过代替。

准备可重复使用的开发样本，覆盖简单单文件、确有必要的多文件、高度依赖而应合并的内容、重复观察、部分观察有依据、全部证据不足、局部与整体风格不同等情况。另覆盖名称用途相近但适用任务不同、执行依赖必要常识前提、阅读者未参与来源分析的情况。小说和文案使用各自适当的材料；开发样本不能直接成为生产提示词中每次必带的长上下文。

示例应包含来源观察、可接受的提炼结果及不合格结果的原因。例如，“对白自然”只是效果描述；“让人物先回应对方话中的压力，而不直接回答字面问题，用动作和省略保留未说出的部分”才是具体写法，但也只有来源支持时才能提炼。示例不是所有技法都必须遵守的新规则。

使用条件与分析说明也要用示例区分：正文可以写“用于危险逼近、需要收窄注意力的局部场景”；“样本仅覆盖两处场景，不能证明全书都使用短句”属于来源分析记录。前者帮助创作选择，后者说明证据范围，不能简单删除证据记录，也不应在每个文件中反复出现。

开发验收分开检查：

- **结构可用性**：入口、引用、完整保存、版本和按需读取符合契约；由确定性检查验证。
- **内容质量**：来源支持、具体可执行、保留有辨识度的处理及必要前提、简洁、拆分必要、内容一致；不以是否新奇为依据排除常见但有效的写法。名称用途能区分适用任务。复核者检查来源依据，独立使用者仅取得入口和所需辅助文件，验证不依赖原文或分析上下文；不只依赖同一次生成的自评。
- **实际使用**：用生成技法从入口完成代表性写作任务，检查读取文件与实际写法；这是开发验收，不是恢复每次用户蒸馏都强制执行的迁移试写流水线。

比较提示词修订时记录来源范围、用户关注点、模型配置、提示词版本、生成文件和失败情况。内容样本与用于调试的示例应有所区分，避免只对演示材料有效。没有足够证据时不宣称提示词已经优秀或跨模型稳定。

2026-09-07 的初稿复核做过一次独立子代理小样例试验，输入为两组人工编写的短观察：危险临近与安全后的叙述变化，以及安静回忆与追逐场景的差异。两组都生成了可由单文件承载的内容，没有强拆目录；同时发现“材料不足以证明什么”的分析说明重复进入正文。该试验用于定位改写方向，未调用 PurrTypos Provider，未验证真实来源、多文件完整生成或本节修订版；不能将其记为 B 线验收完成。

## 6. 页面与交互范围

- 技法库详情：左侧文件目录，标识入口；右侧阅读或编辑当前文件；支持管理辅助文件。只有入口时保持简洁。
- 来源分析结果：展示相同技法结构及文件阅读能力，证据与分析过程单独关联查看；替换“写作方法与迁移检验”等旧内容与保存门槛。
- 方案编辑：选择技法版本，维护可选组合说明，不要求用户管理包内文件。
- 小说绑定与对话输入：呈现授权及已选内容，在输入工具区提供模式和手动添加入口。
- 使用记录：区分可用目录、手动选择和实际读取；正文及私有推理不用于伪造进度或诊断标签。
- 保留 0.6 已规范的分析结果弹窗高度和内部滚动行为，目录切换不能恢复为随内容无限撑高。

## 7. 旧结构与旧数据处理

旧写作技法和写作方案内容不迁移，旧格式不做兼容读取，采用新的存储与运行契约。

实施前列出旧表、接口、内置种子、候选转换、前端类型和运行读取入口。清理旧技法、旧方案及相关绑定，取消旧结构继续写入、启动时重新种入或通过备份导入复活的路径。清理应可重复执行且只作用于已核对范围；“不迁移内容”不等于每次启动清空新数据。

不清空整个数据库，不删除小说正文、来源原文、正史、Story Memory 和其他无关数据。旧分析中嵌入的技法与历史 Run 引用保留为只读历史，不允许通过旧 ID 恢复执行或候选入库；旧备份在恢复可用前完成相同退役。调用者、种子与六张旧表的准确范围已记入旧结构退役清单，不能复用会删除历史 Run 的旧分析清理脚本。

退役器已实现并在隔离库验证；正式用户数据库尚未执行初始化或清理。启动新版将按已确认的六张旧表范围执行一次性退役，保留来源、小说与历史运行。

## 9. 验收标准与验证边界

来源提取、实体归一和概览按各自契约处理冻结文本，不接收最终技法创作要求 `analysisFocus`；该要求在生成阶段完整提供。这样不会把“编写技法、说明如何选用”误当成提取任务。提取优先记录具体文字安排，生成再按用户关注点取舍。

生成保存工具会将待写入文件与冻结观察的证据逐段比对：连续 32 个字母或数字字符相同（忽略标点与空白）时返回文件和行位置，要求原创改写，且不会推进草稿代次。该检查只拦截较长字面复用，不判断语义正确性，不拼接独立证据制造命中，也不应用于用户手动编辑或导入的作者文件。短引用、观点推导和内容质量仍由内容验收判断。

已勾选项表示对应工程或隔离测试范围通过；多文件生命周期为确定性工具验收，不代表模型已自然生成多文件。真实用户库尚未执行退役，跨平台与公开依赖门槛另列。

- [x] 一个 `SKILL.md` 可完成创建、编辑、保存、导出、导入和写作使用，无强制辅助文件。
- [x] 多文件技法保持目录与引用；入口可指导联合使用；断链、循环和越界有明确处理。
- [x] 多文件生成支持逐步完成、失败恢复和取消；未完成草稿不会被自动选用。
- [x] 技法生成不强制固定类别和检查表，不默认创建方案，不依赖迁移试写报告入库。
- [ ] 内置生成规范覆盖提炼、取舍、文件组织、入口编写和修订；生成提示词与最终技法正文职责分明。
- [ ] 名称和用途能说明具体能力与适用时机，帮助选择相近技法；不要求先读全文才能判断用途。
- [ ] 未读过来源、未参与分析的写作者能从入口和必要辅助文件独立使用技法，无隐含原文或分析上下文依赖。
- [ ] 使用条件留在正文，来源覆盖与证据不足说明独立保存；部分有依据时交付成立部分，全部不足时不生成占位技法。
- [ ] 去重和精简保留执行必需的前提；不因属于常识而删除，也不反复复制生成检查要求到技法正文。
- [x] 上游分析、聚合、生成、修订、输出 schema 与内置提示词一致，不再暗含旧的强制正文模板及迁移试写要求。
- [ ] 有单文件、多文件、应合并内容、重复观察、部分有依据与全部不足的样本；分别记录结构检查、人工内容复核与独立使用结果。

- [x] 自动模式只能搜索已授权范围，可选择不用技法；不会把全部授权内容自动注入。
- [x] 仅手动模式没有隐式搜索、旧主方法注入或 Agent 补选；无指定项时正常写作。

确定性测试、界面目录和上下文估算不能证明真实 Provider 的生成质量或 Token/耗时改善。真实性、成本和效果结论需要对应运行证据；没有对照数据时不承诺节省比例。

## 10. P0 收口决策与后续验证

以下规则构成 v1 实施基线。细节的单一维护位置是 P0 契约及两个清单，后续改动同步到对应验收，不能继续由各模块自行推断。

| 事项 | v1 规则 |
| --- | --- |
| 默认模式与继承 | 默认仅手动；小说默认值初始化新会话；会话模式持续保存；手动选择仅本轮；入队/准入冻结请求 |
| 授权与方案 | 小说设置管理准确版本授权；方案授权包含冻结成员；手动指定授予本轮访问；撤销按授权代次生效，恢复不绕过 |
| 手动上传 | 受管理的本轮输入快照，不自动入库；随关联 Run 保留并备份，未来轮次需再次明确选择 |
| 文件和版本 | YAML name/description，辅助 Markdown/TXT，标准相对链接；宿主身份与内容摘要版本分离；方案 JSON 引用固定成员 |
| 草稿与提交 | 草稿 ID、乐观代次、稳定操作 ID；逐文件/批量编辑原子提交；seal 快照与发布分开；定义响应丢失、取消和恢复 |
| 正常无技法结果 | insufficient_material 属于可完成分析，无候选、无保存技法动作；故障与取消不能伪装成不足 |
| 冲突、归档和回收 | 同技法不同版本冲突明确处理；写法冲突依条件取舍；新结构删除为归档，保留引用版本，不自动回收历史 |
| 导入、旧数据与备份 | Markdown/目录/ZIP 导入；方案导出带依赖；旧六表不迁移；历史分析与 Run 只读保留，旧备份先退役后启用 |
| 蒸馏规模 | 首版零个或一个技法、可多文件；观察按预算分批保留与按机制去重，不用固定六条丢弃有效机制 |
| 提示词与样本 | 共同提示词模块位置已指定；当前草案、具体原创样本、真实来源引用及质量判定分别版本化记录 |

尚需完成的是实现与实证验证：工程限额在真实样本上校准、跨平台文件保存与打包验证、真实来源观察复核和 Provider 生成/使用结果。它们是 P1–P5 及 B 线交付，不再作为未定义的产品规则。P0 通过不代表这些测试已经通过。
