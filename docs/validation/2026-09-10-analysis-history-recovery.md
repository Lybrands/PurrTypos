# 小说分析历史恢复重复执行

## 现象与证据

来源 `fbVsV5OV` 长时间停在“正在恢复对话”。只读检查时，后端 health 正常，来源版本 `iCo1LP1h` 的事件接口首包约 0.1 秒返回 HTTP 200。

以正式 limit=500 完整读取：24 页、11986 条事件、8793567 字节，约 0.82 秒传输完成。该测量说明接口可以返回完整历史，不支持“内容超过容量所以无法恢复”的判断。SSE 的连接保持打开属于正常行为，不能把 curl 的最终超时误当成首包失败。

页面原先在事件流首包回调中等待 `hydrateNovelAnalysisHistory`：读取当前根 Run 和全部关联 Run 的完整分页，再重放一次；随后又从零消费同一来源事件流，在 `hasMore=false` 后才解除 initializing。这导致串行重复恢复，长历史会放大等待。

## 修改

- 页面只使用已有来源事件流完成历史恢复与后续实时更新，不再额外读取和重放各 Run 快照。
- 仍在收到完整历史边界后才允许提交，避免把首包等同恢复完成。
- 恢复过程中显示已处理历史记录数。
- 恢复异常后展示错误与“重新恢复”，保留提交禁用状态，不永久显示无说明的转圈。

## 验证边界

- 修复后的页面改动通过 480 项前端测试；类型、组件边界与生产前端构建通过。
- 排查期间该来源出现了新的根 Run。为避免把新任务误当旧任务恢复成功，离线验证固定使用最初读取的 `run_bba8c2fc75a046a5` 元数据及其关联范围。
- 使用只读捕获的实际来源历史，在 Node 中运行当前 `NovelAnalysisConversationStream.applyAsync`：25 页、12273 条事件，约 15.27 秒处理完成；10ms 交互模拟计时器执行 1343 次，最终 hasMore=false。数据在两次读取之间增加，因此数量不同。
- 该结果是实际历史数据的离线重放，不是 Electron 页面完整验收，也不是 Provider 重新执行。没有修改任务数据库或真实创作资料；临时历史副本已删除。
