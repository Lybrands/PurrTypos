## 输出截断原因追查

只读核对上述证据库中的 model.call_recorded、provider.usage、stream.aborted / committed 和工具调用记录：

| 观察子 Run 的第三次模型调用 | 首次失败 | 自动重试成功 |
| --- | --- | --- |
| 单次生成上限 | 16,384 | 16,384 |
| reasoningMode | enabled | enabled |
| 输入 token | 2,328 | 2,448 |
| 生成 token（包含推理） | 16,384 | 10,986 |
| 其中推理 token | 16,383 | 7,923 |
| 结果 | model_output_truncated | submitNovelAnalysisResult 工具调用完成 |

直接原因是首次调用耗尽单次生成预算，几乎全部用于推理，按 Provider 用量统计仅余 1 个非推理生成 token；不是最终分析正文过长，也没有上下文撑满的证据。两次尝试前两轮均调用 listAnalysisObservations，成功重试随后提交结果，第四轮以 stop 正常结束。

16,384 来自 scripts/verify-writing-technique-source.py 显式设置的 max_generation_tokens，不代表用户在界面手动选择了这个值。调用凭据中的 generationSource=user 是框架对显式请求参数的分类；profile 上限为 262,144，没有覆盖该显式预算。宿主网关将有效预算传入 max_tokens，并将 completion_tokens 与其 reasoning_tokens 明细映射到持久化用量；PurrA 将 LENGTH 终止且无工具调用的情况归类为 model_output_truncated。本次持久化流中已确认该错误分类，未取得独立原始 HTTP finish_reason 记录。

本次属于推理耗尽预算，与 0.5.0 的推理配置冲突不同。相同预算重试成功说明存在调用间差异；一次样本不能判定为模型缺陷、提示词死循环或稳定的预算不足。未读取或公开私有推理正文，未为调查追加模型调用。

后续预算优化应单独比较推理消耗、结果所需容量、失败率和重试成本，再决定是否调整；该变更不直接提高上限或关闭推理。流水线最终完成不等于消除了首次截断和额外调用成本。
