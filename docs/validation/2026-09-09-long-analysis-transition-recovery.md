# 长篇来源分析阶段冲突与恢复

## 状态

代码修复已实施；确定性回归及真实数据库副本恢复已验证。尚未用更新后的后端恢复真实任务，也没有新增真实 Provider 完整长任务或 Electron 验收结果。

## 根因证据

`run_0837fef4fb7949f9` 对应 109 单元的分析任务，暂停时任务统计为 34 个完成；第 38 个提取单元以 `execution_interrupted` 回到 pending。没有用户取消请求。根 Run 仍为 running。

旧 recipe v6 按单元索引均分到 3 个模型计划步骤，将第 38 个提取单元分入第二步，前一步仍有提取单元在运行。PurrA 的 RunSnapshot 要求同一时刻只能有一个执行中的计划步骤；同时同步两步为 running 可确定性复现 ValueError。进度确认异常进入执行清理，触发单元中断和任务暂停。

## 修复

- recipe v7 按业务执行阶段分组；跨计划步骤添加依赖屏障，保留阶段内部并行。模型计划步骤较多时拆分阶段并保持依赖边界，不新增计划数量上限。
- 调度进度异常先发出停止信号、持久化任务检查点，再通过公开 RunStateMachine / RunCommit 与项目 output repository 原子写入根 Run 失败事件和界面生命周期记录。错误收尾抵御消费者取消，保留原始失败原因。
- 恢复旧任务时更新调度依赖与 plannerStepId、重新投影计划完成状态；保留冻结输入、完成输出、子 Run 绑定。仍有子 Run 活跃时拒绝恢复，避免重复调用。遗留租约释放后复用已完成子 Run 的既有执行机制。
- 冻结元数据通过 thaw_json_mapping 转换后持久化，避免嵌套 FrozenList 导致恢复失败。
- 没有修改 PurrA 框架、安装包、用户原始数据库或创作资料。
