- 保留内部多模式和可选组合；E02 的组合建议没有强迫两种模式同时使用，不能认定为违约。也不要求用户必须预先列出每个分支。

- analysisFocus 的表达不能证明造成了发散，暂不修改共享阶段提示词。校准示例的锚定效应也未得到对照验证，保留当前简短示例及其适用边界。
- readTechniqueSource 可核对或反驳已有观察；返回文本不创建 observation ID。独立新结论不能用无关旧 ID 冒充证据。当前 evidenceRefs 校验只保证 ID 属于冻结观察，不能证明语义支持；该变更不新增观察生产阶段，也不把该风险声称为已复现的故障。

Skill Creator 第二遍复核结论：上述修改保留开放式技法组织、单入口与按需辅助文件；没有引入强制格式、原文之外的写作规则或新审查循环。该模块是应用内生成指令，不是 Codex 技能目录，不运行仅检查技能 frontmatter 的 quick_validate 来冒充生成质量验证。

## 结论

目标与产物形态合理，但阶段职责、工具契约和提示词没有彻底分离。首要问题是实际仍要求重复工作，不能仅靠缩短文案或增加“不要发散”解决。静态审查只能确认指令和契约问题，不能证明这些问题导致某次推理截断，也不能保证修改后的成本收益。

## 按优先级排列的发现

1. 高：概览仍承担完整分析重写。`backend/application/novel_analysis_executor.py:928` 要求返回 facts、craftCards、storyOverview，931 要求浏览全部观察并语义合并。它不是只补概览，与提取/归一及生成阶段的处理范围重叠。建议先将概览结果收窄为 storyOverview，代码保留已有 facts/craftCards 并装配结果；同步修改提交 schema、校验和消费方，不能只改提示词。是否必须独立生成概览，应依据产品展示需要判断，不机械增加或删掉阶段。

2. 中：创作判断与确定性检查混在提交前复核中。`backend/domains/writing_technique_prompts.py:17` 同时要求复核内容、文件完整性和引用有效性；31-33 及工具本身又定义并校验文件/版本/引用契约。写作者仍需知道入口和链接的使用规则，但不应再次承担程序可判断的合法性审核。将路径、版本、文件存在等检查由工具给出结构化错误，模型只修复指出的问题；内容是否协调仍是语义判断，不能交给简单脚本假装解决。

3. 中：补读和完成标准可执行性不足。32 的“需要补读时”未说明读取的目的；17 的“按上述标准复核”仍可能导致宽泛复查。宿主已有“提交成功后结束”（executor:123），校准示例也有完成提示，因此不是完全没有停止条件。缺的是提交前判断：信息足以支持写法与必要使用条件时交付；仅当具体待用结论有缺口或矛盾时补读相关范围，不将浏览全量原文作为默认动作。这是减少无效工作，不是要求忽略反证或降低质量标准。

4. 中：所有生成调用无条件拼接完整校准例子。`build_generation_prompt():24` 拼接核心指引、工具说明与 E01 小说节奏示例，虽然三者分成常量，模型仍全部接收。对不同文体任务可能增加无关上下文和示例倾向；不能据此认定已造成某次错误。保留能澄清抽象尺度的最小示例，或用真实可用的按需参考机制加载；仅拆成文件而仍全量注入没有收益。

5. 低：协议说明分散维护。入口规则在核心指引和文件指导均出现，提交字段同时出现在文件指导、输入 submissionContract 与工具 schema；通用 executor 又重复完整提交要求。保留必要的使用语义及冲突恢复约束，将详细字段归工具契约维护，减少多处漂移。不能因去重删掉并发修改版本检查、冻结来源范围或提交不等于发布等真实不变量。

## 应保留的设计

- 从原文写法提炼可独立使用的技法，优先写作决策而非分析报告。
- SKILL.md 单入口，单文件可完整交付，多文件仅在有独立用途时采用；无固定目录/章节数量。
- 来源证据单独保存，用户使用的正文不依赖原文剧情或人物模板。
- 材料不足可以提交明确结果；模型或工具执行失败不能伪装成材料不足。
- 技法封存不等于发布或授权，版本冲突先重读。

## 优先修改范围

第一类问题的修复范围：先缩小概览职责与输出协议，再精简重复说明、定义补读和完成条件。核心生成指引保留目的、证据边界、文件组织决策和交付条件即可，不另造多轮自审流程。第二类语义准确性问题继续单独记录，本次不实施。

验收需同时记录单次生成峰值、截断/失败重试、全程生成及输入 token、模型调用次数和耗时；质量另外判定。不能以格式校验器或一次样本成功证明提示词质量，不能只报告峰值下降而忽略全程消耗上升。
